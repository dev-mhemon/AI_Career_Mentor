### Concrete Option 2B design proposal and Option A completion gate investigation

Based on empirical D05 findings, repository contracts, and Codex review findings, the following concrete design is proposed for review:

#### 1. Registration completion gate, trusted completion writer, and RLS/access inventory

##### A. Trusted Completion Writer Authority

- **Exclusive Authority:** Only the backend endpoint **C05 EP-A02 (`POST /api/v1/auth/verify-email`)** is authorized to transition an email registration from pending (`verified_contact = false`) to complete (`verified_contact = true`, `user_auth_providers.verified_at = now()`).
- **Required Completion Proof:** Valid submission of the 6-digit OTP satisfying R31 Redis abuse control (`auth:v1:challenge:<contact_digest>`) and secret-store verification within the 600-second window.
- **Strict Invariant:** A confirmed Supabase Auth email (`auth.users.email_confirmed_at IS NOT NULL`) or a valid Supabase JWT alone **MUST NOT** complete an A01 registration or mark `public.users.verified_contact = true`.

##### B. /auth/sync Eligibility Rules and Promotion Prevention

In `backend/src/auth/services/auth.service.ts` (`AuthService.bootstrap`), lines 86–91 currently update `public.users` on conflict with `verified_contact = !!(email || phone)` where `email = user.email_confirmed_at ? user.email : null`. If GoTrue confirms an email outside A02 (e.g. via direct public `/auth/v1/verify`), a subsequent call to `/auth/sync` would promote `verified_contact` to `true`, bypassing backend R31 OTP controls entirely.

To prevent this bypass, `/auth/sync` must enforce explicit eligibility checks across four distinct caller classes:

1. **Pending A01 email registration (`public.user_auth_providers` contains `provider = 'email'` with `verified_at IS NULL`, or `public.users.verified_contact = false`):**

   - Even if GoTrue confirms the email (resulting in `email_confirmed_at IS NOT NULL`), `/auth/sync` **MUST NOT** promote `verified_contact` to `true` or set `verified_at = now()`.

   - `/auth/sync` explicitly checks for pending email registration rows; if unverified via EP-A02 in the application database, `/auth/sync` refuses promotion, returning unverified status (`verified_contact: false`) or rejecting with HTTP `403 UNVERIFIED_ACCOUNT`.

   - C05 `AuthSessionDTO` defines only `next_step: 'profile_setup' | 'app_home'`; undocumented values such as `'verify_email'` are NOT used. GoTrue email confirmation alone must never complete an A01 email registration.

2. **Confirmed email JWT with no application row (e.g. user created directly in GoTrue or externally without A01):**

   - `/auth/sync` **MUST NOT** synthesize or invent an A01 completion. It cannot promote an un-registered GoTrue user into a fully verified application user. It rejects or creates an unverified pending record (`verified_contact = false`) requiring proper registration initiation.

3. **Existing verified account (`public.users.verified_contact = true` and `verified_at IS NOT NULL`):**

   - Normal synchronization occurs (updating `last_login_at`, `last_active_at`, and linked providers).

   - `/auth/sync` cannot downgrade an already verified contact to false.

4. **OAuth identity (`google`, `facebook` via external provider token/session):**

   - Provisioning and identity linking occur via C05 EP-A10 (`POST /api/v1/auth/oauth/session`, implemented in `AuthController`) or authorized OAuth sync.

   - If the external OAuth provider verified the email, `verified_contact = true` is set for the OAuth account.

   - If the OAuth provider lacks an email or did not verify contact (e.g. phone-only Facebook), `verified_contact` remains `false` until an email/phone is added and verified via EP-A02/A03 (`next_step: 'add_verified_contact'`).

   - **Strict Invariant:** OAuth is strictly an external provider flow and is **NOT** an alternative completion writer for a pending A01 email registration (`provider = 'email'`).

##### C. Route Exceptions and Preserving Legitimate Access

- **Unverified OAuth contact-add (`EP-A12`):** Permitted for unverified OAuth users (`next_step: 'add_verified_contact'`) or existing accounts adding an additional contact via `POST /api/v1/auth/contact` (C05 EP-A12; currently unimplemented in backend `AuthController`). Uses Bearer JWT authentication (`H-AUTH`), initiating verification via EP-A02/A03.
- **Account status inspection (`GET /api/v1/auth/me`):** Permitted for authenticated users including suspended users (`@Policy({ allowSuspended: true })`) per C05 EP-A13 and PRD §13, returning `status: 'suspended'` and `can_delete_account: true`. Permitted also for unverified users to inspect their account status (`verified_contact: false`).
- **Permitted account deletion and status read (ADR-020, C05 §14.2):** Suspended users are explicitly permitted to submit an in-app account deletion request via EP-X01 (`POST /api/v1/account/deletion-requests`, `AZ-SUSP`, PRD §7/§13). However, unverified-contact restrictions strictly apply where C05 specifies `VERIFIED_CONTACT_REQUIRED` (`HTTP 403`), so unverified accounts (including applicable unverified OAuth accounts) cannot submit a deletion request until contact verification is satisfied. Reading current deletion status via EP-X02 (`GET /api/v1/account/deletion-requests/current`) is permitted using an account JWT (`AZ-SUSP`) or a route-scoped `DeletionReceipt` to track request progress or tombstone completion without re-opening application feature access.
- **Existing verified accounts:** Full access to feature routes and reference data per role.
- **Suspended accounts (`status = 'suspended'`):** Blocked from all reference data and protected feature routes. In accordance with C05 AZ-SUSP (C05 §14.1–14.2, PRD §7/§13), access is strictly restricted to logout (EP-A06 `POST /api/v1/auth/logout`), account inspection (EP-A13 `GET /api/v1/auth/me` returning `status: 'suspended'` and `can_delete_account: true`), deletion request submission with required confirmation and credentials (EP-X01 `POST /api/v1/account/deletion-requests`), and deletion status read (EP-X02 `GET /api/v1/account/deletion-requests/current`). Ordinary feature access remains strictly gated.
- **Ordinary feature access remains strictly gated:** Incomplete/unverified accounts (`verified_contact = false`) are blocked from all application business routes, career paths, goals, learning resources, etc. OAuth is not an alternative completion writer for A01.

Gating `AccessGuard` to check `SELECT status, verified_contact FROM public.users` and reject with `403 UNVERIFIED_ACCOUNT` if `!u.verified_contact` on non-bootstrap routes is strictly **PROPOSED** and NOT implemented in current source.
- **Direct PostgREST Enforcement:** PostgreSQL RLS policies in `017_rls.sql` currently check only `u.status = 'active'`. Gating RLS on `u.verified_contact = true` is strictly **PROPOSED** and NOT implemented in current schema. A separately reviewed forward migration is required.
- **Status:** Neither the NestJS guard nor the PostgREST RLS currently prevents active accounts with `verified_contact = false` from accessing protected endpoints or reading reference tables. The completion and access gate remains **PROPOSED and UNRESOLVED**.

#### 2. Proposed A02 recovery state machine (`/api/v1/auth/verify-email`)

The A02 endpoint (`POST /api/v1/auth/verify-email`, operation EP-A02) is currently **NOT IMPLEMENTED** (`SPECIFIED, backend absent` in `docs/05-api/openapi.yaml`; route is absent from `backend/src/auth/controllers/auth.controller.ts`).

Furthermore, no `/api/v1/auth/login` endpoint exists in NestJS. Client password login is performed directly against Supabase GoTrue via `supabase.auth.signInWithPassword({ email, password })`. Direct password login is a recovery fallback, NOT A02 success (it does not return C05 `AuthSessionDTO`).

Cross-system atomicity between GoTrue and PostgreSQL does not exist; failure can occur at each step. Session minting via GoTrue is strictly **NON-IDEMPOTENT** (D05 observed session count increase from 1 to 2). A02 cannot blindly replay session minting without risking session proliferation.

When designed, the verification and recovery state machine across failure boundaries is:

```

  |      |       - User cannot bypass via client password login + /auth/sync (sync refuses to promote unverified email registration).
```

- **Endpoint Path:** `/api/v1/auth/verify-email` (EP-A02 in `docs/05-api/openapi.yaml`).

  - `refresh_token: string`

  - `expires_in: number`

  - `token_type: 'Bearer'`

    - `id: UUID`

    - `email: string | null`

    - `phone: string | null`

    - `linked_providers: AuthProviderType[]`

#### 4. Action-specific Send Email hook policy proposal

In GoTrue, when `[auth.hook.send_email]` is enabled, the Postgres function receives an event with the documented discriminator:

`event->'email_data'->>'email_action_type'`.

- **Supported Action Names:**

  - `signup`: covers signup confirmation email delivery, including when triggered via the public `/auth/v1/resend` HTTP route with `{ type: "signup", email }`. The HTTP route is `/resend`, but the mail action discriminator is `signup`.

  - `recovery`: for password reset.

  - `invite`: for user invitations.

  - `email_change`: for email address changes.

  - `magiclink`: for magic links. (Ephemeral links generated via `admin.generateLink` during A02 do not send email, but the action name is `magiclink`).

- **Hook Mechanics & Empirical Scope:**

  - On local D05, a rejecting Send Email hook caused GoTrue token/cooldown changes to roll back in exactly two measured `/auth/v1/resend` cases (`Case 2A` and `Case 2B`). Rollback effects for other actions remain `UNKNOWN`.

  - Returning success (`{}`) tells GoTrue that the hook handled delivery; **GoTrue does NOT fall through to built-in SMTP**! Built-in SMTP is completely skipped.

  - Describing a successful hook return as "harmless suppression" or "SMTP fall-through" is incorrect; returning `{}` without an external mailer silently drops emails.

  - Effects of a successful hook return (`{}`) and effects on other actions (`recovery`, `invite`, `email_change`, `magiclink`) remain **UNKNOWN** and unverified on D05.

- **Action-by-Action Policy Proposal (Requires Owner Decision):**

  - `signup`: Reject or absorb, because registration OTP generation and delivery is handled directly by the application backend mailer service.

  - `recovery`: Returning an error breaks password reset; returning `{}` without a dispatch worker drops reset emails. To support recovery, the hook must invoke an external notification worker or password reset must be managed by a dedicated backend endpoint.

  - `invite` & `email_change`: Cannot be silently suppressed; requires external mailer dispatch or backend route ownership.

  - `magiclink`: Ephemeral magic links generated via `admin.generateLink` during A02 do not invoke the Send Email hook.

- The entire hook policy remains a **PROPOSAL** pending owner decision.

#### 5. OTP lifecycle, separate send window, and secret-store boundaries

- **Timing Windows:**

  - OTP Validity: Exactly **600 seconds** (`AUTH_OTP_TTL_SECONDS = 600`, matching R31).

  - Contact Send Window: Separate **900-second** rate limit window (`AUTH_SEND_WINDOW_SECONDS = 900`, max 3 sends per contact, 10 per IP).

  - Resend Cooldown: **60 seconds** (`AUTH_RESEND_COOLDOWN_SECONDS = 60`).

- **Actual Backend Abuse Control:** In the codebase, abuse control is implemented in [`backend/src/auth/abuse-control/abuse-control.service.ts`](../../../backend/src/auth/abuse-control/abuse-control.service.ts) (`AuthAbuseControl`) using Redis keys:

  - `auth:v1:challenge:<contact_digest>` (stores `{ generation, failures, consumed, busy }`).

  - `auth:v1:send:cooldown:<contact_digest>`.

  - `auth:v1:send:contact:<contact_digest>`.

  - `auth:v1:send:ip:<ip_digest>`.

  - `auth:v1:policy:<policy_digest>`.

- **Existing Rule:** `AuthAbuseControl` tracks attempt counts and lockouts in Redis via Lua scripts (`challengeScript`), but **does not store the OTP or its digest** (`"Store only an opaque generation and attempt state, never the OTP or its digest"`). Redis is R31's atomic attempt/consume authority.
- **Unapproved Secret-Store Candidates:**

  - **Candidate S1 (Dedicated Redis Challenge Store with Server Pepper):** Stored in Redis key `otp:secret:{user_id}` (`TTL = 600s`) holding `{ challenge_id, user_id, digest: hmac_sha256(AUTH_OTP_HMAC_SECRET, user_id + ":" + challenge_id + ":" + otp), expires_at }`. Comparison uses `crypto.timingSafeEqual`.

  - **Candidate S2 (Dedicated PostgreSQL Challenge Table):** A forward migration introducing `private.auth_otp_challenges (user_id uuid primary key, challenge_id uuid, otp_hash text, expires_at timestamptz)` accessible only by the backend application role, never exposed via PostgREST. Redis retains authoritative attempt/consume state.

  - **Storage Gate:** Neither S1 nor S2 is authorized today; putting an OTP digest in Redis is not approved. If Candidate S2 proposes moving challenge attempt tracking to PostgreSQL, that requires a **scoped R31 specification change**. Both remain unapproved proposals requiring an explicit owner secret-store decision.

### Failure, recovery, and residual-risk results

- Exact-session approval retry is idempotent at the application row; it does not claim provider session minting is idempotent. A lost EP-A05/EP-A10 response after approval can leave an active approved session whose tokens did not reach the intended client; retrying provider authentication can create another session and approval. No automatic single-session revocation policy is implemented.
- A pending session does not become usable merely because `verified_contact` later becomes true or because the JWT is refreshed with the same unapproved `session_id`.
- A public-verify-created session remains denied unless a trusted backend path separately approves that exact session. Public `/auth/v1/verify` still bypasses the R31 Redis consume/five-failure authority; this gate limits application access and does not make the provider route enforce R31.

This was deliberately asserted in D05 rather than hidden. Choice 1 therefore does not contain theft after trusted approval, and production acceptance requires an explicit residual-risk decision or a separately supported stronger binding.
