# M03-02 — Re-Authentication, Atomic Cascade Execution & Tombstone Preservation (`EP-X01` / `EP-X02`)

Task / goal / observable acceptance:
- Implement Phase 1 Slice `M03-02` (`Re-Authentication, Atomic Cascade Execution & Tombstone Preservation`) per `docs/07-planning/master-execution-plan.md` §4 and §5:
  - Deliverable 1 — Live Re-Authentication Authority (`backend/src/account/services/reauth-verification.service.ts`):
    - Enforces live re-authentication on `POST /api/v1/account/deletion-requests` (`EP-X01`) without mutating caller session cookies.
    - Password accounts: resolves caller identifier (`email` or `phone`) from `public.users` or `public.user_auth_providers`, calls GoTrue `/auth/v1/token?grant_type=password`, verifies returned subject identity matches caller UUID, and rejects missing/invalid passwords or accounts lacking password configuration with `401 REAUTH_REQUIRED`.
    - OAuth / passwordless accounts: verifies supplied `reauth_token` against GoTrue `/auth/v1/user`, asserts token subject matches caller UUID, and rejects missing, invalid, or expired tokens with `401 REAUTH_REQUIRED`.
    - Fails with `503 SERVICE_UNAVAILABLE` when identity provider is unreachable or times out.
  - Deliverable 2 — Idempotency & Error Contract Alignment (`backend/src/account/dto/account-deletion.dto.ts` & `AccountController`):
    - Aligns `confirmation !== 'DELETE'` with canonical contract `422 CONFIRMATION_MISMATCH` (replacing M03-01's transitional 400).
    - Requires either `password` or `reauth_token`, failing with `401 REAUTH_REQUIRED` when both are omitted, and `400 INVALID_FORMAT` when both are supplied simultaneously.
    - Validates optional `Idempotency-Key` header (`H-IDEM`, UUID format, failing with `400 INVALID_FORMAT` on malformed keys).
    - Enforces 24-hour caller-scoped (`userId + Idempotency-Key`) process-local in-memory idempotency store with TTL eviction, capacity bounding via write-path slot reservation (`reserveSlot = true`), and in-flight concurrent request protection (`409 DELETION_ALREADY_REQUESTED`). Same payload replays cached `202` response; differing payload with same key returns `409 IDEMPOTENCY_KEY_REUSED`. Because completed deletion immediately revokes `private.approved_auth_sessions` and deletes `public.users`, post-completion HTTP replays to `EP-X01` using the revoked Bearer JWT cannot succeed over HTTP (rejected with `401` at `DeletionReceiptGuard` before reaching the controller; `EP-X02` with `DeletionReceipt` is the post-deletion status recovery path); the in-memory idempotency store and in-flight lock serve concurrent/in-flight deduplication and direct service-level callers during `M03-02`.
  - Deliverable 3 — Atomic Cascade Execution, Session Revocation & Tombstone Preservation (`R05`, `R06`):
    - Executes the entire local account deletion lifecycle inside a single atomic database transaction (`this.database.transaction(userId, ...)` with `active = false` and `foreground = false`):
      1. Inserts or transitions active request row in `public.account_deletion_requests` (`status = 'in_progress'`), translating unique constraint violation `23505` (`uq_account_deletion_one_active`) to `409 DELETION_ALREADY_REQUESTED`.
      2. Revokes all active user sessions in `private.approved_auth_sessions` (`revoked_at = clock_timestamp()`, `updated_at = clock_timestamp()`).
      3. Revokes GoTrue auth refresh tokens (`auth.refresh_tokens`) and deletes GoTrue sessions (`auth.sessions`) fail-closed so any database failure aborts and rolls back the entire transaction.
      4. Deletes user row from `public.users` (`DELETE FROM public.users WHERE id = $1::uuid`), firing database trigger `trg_users_complete_deletion` (`BEFORE DELETE ON public.users FOR EACH ROW` executing `private.complete_deletion_on_user_delete()`) which atomically transitions the deletion request to `status = 'completed'`, `completed_at = clock_timestamp()`, and foreign key `ON DELETE SET NULL` sets `user_id = NULL` (`R05`).
      5. Strictly validates completed tombstone row directly from DB (never fabricating synthetic status in production; throws `500 DATABASE_ERROR` and rolls back if row is missing, status is not 'completed', or `user_id` is retained) and mints a 24-hour HMAC-SHA256 `DeletionReceipt` (`R06`).
      6. Verifies that if `DELETE FROM public.users` fails, the transaction rolls back completely without committing completed status (`R05`).
  - Deliverable 4 — Status Inspection (`EP-X02`) & Tombstone Verification:
    - Confirms `GET /api/v1/account/deletion-requests/current` (`EP-X02`) authenticated with `Authorization: DeletionReceipt <receipt>` returns `200` with `status: 'completed'`, `completed_at` populated, and `user_id: null` on completed tombstones.
  - Deliverable 5 — OpenAPI Contract Sync (`docs/05-api/openapi.yaml`):
    - Synchronized `EP-X01` and `EP-X02` operational notes, error codes (`422 CONFIRMATION_MISMATCH`, `401 REAUTH_REQUIRED`, `409 IDEMPOTENCY_KEY_REUSED`), parameter notes (`IdempotencyKey`), and DTO schemas, documenting that re-authentication, atomic cascade, and tombstone completion are active in `M03-02`, while noting that encrypted `provider_cleanup` outbox retries and 90d/30d retention purge runners belong to `M03-03`.
  - Deliverable 6 — Deterministic Unit & Synthetic Integration Tests (`backend/src/account/account-deletion.spec.ts`):
    - Expanded test suite from 18 to 41 tests, strictly adhering to zero-parser mock rules (inspecting positional parameters and simple keyword checks), verifying all credential combinations, rollback atomicity, caller-scoped idempotency key replay/conflict, cache eviction/capacity limits, in-flight race protection, fail-closed GoTrue cleanup rollback, strict tombstone validation, and suspended-account deletion.
