# M03-01 — Account Deletion Wire Contract, Deletion Receipt Authority & Status Query (`EP-X01` / `EP-X02`)

Task / goal / observable acceptance:
- Implement Phase 1 Slice `M03-01` (`Account Deletion Wire Contract, Deletion Receipt Authority & Status Query`) per `docs/07-planning/master-execution-plan.md` §4 and §5:
  - Deliverable 1 — OpenAPI Wire Contract (`docs/05-api/openapi.yaml`):
    - Added `POST /api/v1/account/deletion-requests` (`EP-X01`) and `GET /api/v1/account/deletion-requests/current` (`EP-X02`).
    - Defined `AccountDeletionRequestDTO` (`confirmation: "DELETE"`, optional `password`, optional `reauth_token`), `AccountDeletionStatusDTO` (`id`, `status` enum `scheduled | in_progress | completed`, `requested_at`, `completed_at`, `provider_deletion_requested`, optional `deletion_receipt`, optional `receipt_expires_at`), `AccountDeletionStatusDTOEnvelope`, `DeletionReceipt` security scheme, and `IdempotencyKey` (`H-IDEM`) header parameter.
    - Documented `AZ-SUSP` suspended-user access, dual authentication on `EP-X02` (Bearer JWT OR `Authorization: DeletionReceipt <token>`), error codes (`400`, `401`, `403`, `404`, `409 DELETION_ALREADY_REQUESTED`, `422`, `500`, `503`), and the explicit boundary between `M03-01` (`scheduled` row persistence, `DeletionReceipt` minting/verification, `AZ-SUSP` access, status lookup including `user_id = NULL` completed tombstones) and `M03-02` (live password/OAuth re-authentication verification, atomic cascade deletion, and session revocation).
  - Deliverable 2 — Deletion Receipt HMAC-SHA256 Authority (`backend/src/account/services/deletion-receipt.service.ts`):
    - Mints and verifies compact HMAC-SHA256 signed `DeletionReceipt` tokens with zero-PII claims `{ typ: 'deletion_receipt', request_id, aud: 'account-deletion-status', iat, exp }` (`exp` = 24 hours from issue per `R06`).
    - Performs constant-time signature comparison via `crypto.timingSafeEqual` on equal-length byte buffers, validates `typ`, `aud`, `request_id` (UUID format), `iat`, and `exp` strictly, fails closed (`503 SERVICE_UNAVAILABLE`) whenever the signing secret is missing or shorter than 32 bytes outside explicit `test` / `development` environments, and provides a deterministic fallback in `test` and `development` environments.
  - Deliverable 3 — `AZ-SUSP` & Dual-Auth Guard (`backend/src/account/guards/deletion-receipt.guard.ts`):
    - Requires `SupabaseAuthGuard` at bootstrap (fail-closed constructor / `OnModuleInit` check, zero unverified JWT payload decoding fallback) and delegates all `Authorization: Bearer <jwt>` cryptographic verification to `SupabaseAuthGuard.canActivate(...)`.
    - Permits both `active` and `suspended` accounts (`AZ-SUSP`) on `EP-X01` and `EP-X02` while requiring `verified_contact === true` (`403 VERIFIED_CONTACT_REQUIRED` on `false`, `null`, or `undefined`) and an active approved session in `private.approved_auth_sessions` (`401 AUTH_REQUIRED`) for Bearer JWT callers.
    - On `EP-X02` (`@AllowDeletionReceipt()`), accepts EITHER `Authorization: DeletionReceipt <token>` (scoped strictly to `claims.request_id` per `R06`, bypassing user/session lookup so completed `user_id = NULL` tombstones can be queried) OR `Authorization: Bearer <jwt>`. Rejects missing, malformed, or unsupported authorization schemes with `401`.
  - Deliverable 4 — Account Deletion Service, Controller & Module (`backend/src/account/`):
    - `AccountDeletionService.requestDeletion(userId, dto)`: validates `confirmation === 'DELETE'` (`400 CONFIRMATION_MISMATCH`), inserts a `scheduled` row into `public.account_deletion_requests` (`provider_deletion_requested = false`, `provider_cleanup = '[]'::jsonb`, `provider_cleanup_expires_at = now() + interval '30 days'`) and mints a 24-hour `DeletionReceipt` inside the database transaction callback (so any `503` receipt failure rolls back the row insertion), maps PostgreSQL unique constraint violation `23505` (`uq_account_deletion_one_active`) to `409 DELETION_ALREADY_REQUESTED`, and returns the `202` payload.
    - `AccountDeletionService.getCurrentStatus(authContext)`: queries `public.account_deletion_requests` by `id = request_id` when authenticated via `DeletionReceipt` (returning the row even when `user_id IS NULL`) or queries the latest request for `user_id` when authenticated via Bearer JWT; throws `404 DELETION_REQUEST_NOT_FOUND` when no row exists.
    - Wired `AccountController` and `AccountModule` (providing and exporting `SupabaseAuthGuard`) into `AppModule` with 100% JSDoc coverage.
  - Deliverable 5 — Deterministic Unit & Integration Tests (`backend/src/account/**/*.spec.ts`):
    - `backend/src/account/services/deletion-receipt.service.spec.ts` (10 tests) and `backend/src/account/account-deletion.spec.ts` (18 tests), using simple positional parameter assertions (`expect(mockQuery).toHaveBeenCalledWith(expect.any(String), [...])`) and `vi.clearAllMocks()` in `beforeEach`.

Explicit M03-01 vs M03-02 scope boundary:
- Enforced in `M03-01`:
  - `EP-X01` (`POST /api/v1/account/deletion-requests`) wire contract, `confirmation === 'DELETE'` validation (`400 CONFIRMATION_MISMATCH`), `AZ-SUSP` access (`active` and `suspended` accounts with `verified_contact = true` and approved session in `private.approved_auth_sessions`), persistence of `scheduled` row in `public.account_deletion_requests` with `23505` (`uq_account_deletion_one_active`) mapped to `409 DELETION_ALREADY_REQUESTED`, and 24-hour HMAC-SHA256 `DeletionReceipt` minting (`R06`).
  - `EP-X02` (`GET /api/v1/account/deletion-requests/current`) dual authentication (`Authorization: Bearer <jwt>` or `Authorization: DeletionReceipt <token>`), `DeletionReceipt` verification (`R06`), status lookup for active (`scheduled` / `in_progress`) and completed null-owner tombstone (`user_id = NULL`, `status = 'completed'`) rows, and `404 DELETION_REQUEST_NOT_FOUND` when no row exists.
- Deferred to `M03-02`:
  - Live password / OAuth `reauth_token` verification against GoTrue before scheduling/executing deletion (`401 REAUTH_REQUIRED`).
  - Deletion worker execution, atomic local cascade deletion via `auth.users` -> `public.users` (`private.complete_deletion_on_user_delete()`), immediate session revocation, and external provider cleanup outbox processing (`R05`, `R35`).
