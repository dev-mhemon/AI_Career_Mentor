R31 defaults remain configurable positive bounded integers: OTP 600s/5 failures, resend 60s, send 3/contact and 10/IP per 900s, login 5 failures per identifier+IP/900s and separate 900s lockout. Six-digit code syntax comes from C05 A02/VerifyCodeRequestDTO. Provider validity caps the effective configured challenge TTL. No SQL system_configurations key or immutable product threshold is invented.

All keys use `auth:v1` plus domain-separated HMAC-SHA256 contact/IP components. Login combines the protected identifier and canonical IP; IPv6 alternate spellings and IPv4-mapped IPv6 share the same effective address. Callers supply validated normalized contacts and a trusted client IP. No raw contact, IP, password, OTP/OTP digest, session token, Redis credentials or HMAC secret is stored in Redis keys/state or emitted by the boundary.

An atomic HMAC policy fingerprint rejects inconsistent R31 settings from independent instances sharing a secret. Its intentionally refreshed TTL covers the longest configured state lifetime; counter and challenge TTLs remain fixed. Changed R31 settings become active after old traffic stops and marker/state expires, or through a separately reviewed migration. Timeout/retry settings are excluded from this fingerprint. Required-expiry counter corruption fails closed instead of silently repairing/sliding the window.

Send admission atomically checks cooldown and both budgets before incrementing, sets counter expiry only on first increment, and reserves quota before provider delivery. Rejected sends do not extend TTLs or consume extra quota; accepted attempts are not refunded after delivery failure. Unknown contacts must follow the same reservation path; endpoint masking/timing remains later work.

Challenge state contains only opaque generation/operation ownership, failure count and consumed flag. Verification reserves the current generation in Redis before the provider callback, then atomically compares generation/owner and consumes once or records a failure. Fifth default failure returns VERIFICATION_ATTEMPTS_EXCEEDED 429. Expired/missing generation returns 410; consumed challenge returns 409. Replacement invalidates old in-flight completion. No generation field is added to HTTP DTOs. The actual OTP stays only in memory and in the approved provider/secret-store boundary; this helper generates no OTP and selects no provider.

Login callbacks are serialized per identifier+IP so concurrent failures cannot skip the threshold. The first confirmed failure starts a fixed window; the fifth starts a separate lockout. Successful login clears that pair's failures. Other identifiers on the same IP remain usable. Redis unavailability fails login closed as explicitly requested for this task, extending the minimum R31 send/verify outage rule without claiming endpoint integration.

Occupied challenge/login reservations return retryable 503 with their remaining TTL. Unexpected provider exceptions retain ownership until expiry instead of retrying an ambiguous external operation. Safe 503 also covers missing configuration, connection failure, command deadline and shutdown. Complete valid configuration is checked when supplied; entirely absent configuration permits existing routes to boot but all helper operations fail closed. No offline queue or automatic command replay. Safe exceptions use the existing HTTP formatter, numeric retryAfterSeconds and Retry-After; the pre-existing nullable optional-field discrepancy outside these responses remains ES-05.

Supported infrastructure is one standalone Redis 7+ authority with noeviction and consistent policy/secret on every app instance; multi-slot Redis Cluster is unsupported. Secret rotation changes the effective keyspace and requires coordinated operational review. Generic idempotency/loss-epoch recovery, durable queues, provider bypass controls and provider/session reconciliation remain outside M01-02.
