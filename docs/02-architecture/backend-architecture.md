Bootstrap upserts users/providers/profile/preferences under one application transaction; status is preserved. It stamps login/activity on every sync/bootstrap. A13 is a passive read. Thus reusing bootstrap for refresh would violate R24. A synthetic signed unverified identity is already provisioned by the existing HTTP fixture with null contacts and `verified_contact=false`; “confirmed-contact mapping” does not mean bootstrap refuses every unverified identity. Provider confirmation must prevent email/password session issuance, and the canonical flow must not expose tokens before mapping succeeds.

## Proposed canonical session handoff

Engineering proposal for M01-04/06/07/08 review; no new wire fields or internal HTTP endpoints. Retain the existing SSR cookie adapter/PKCE OAuth boundary. NestJS owns canonical validation, R31 counters/error translation, trusted provisioning and app state. The SDK owns session serialization/chunking and provider identity reads, not application policy.

1. Existing Next Server Actions send canonical A01/A02/A04/A05 DTOs to NestJS. Signup/resend return only RegistrationPendingDTO. A02/A05 return AuthSessionDTO only after live provider identity checks and successful app mapping. Do not return token payloads through client form state or store them in the R18 draft.
2. In a writable Server Action/handler, install the fresh canonical token pair with SDK `setSession({access_token, refresh_token})` using the existing request-scoped server client. Require success before redirect; retrieve app routing/status from canonical DTO/A13, never from cookie user metadata. If installation fails after provider success, retain no usable browser session and offer login recovery; do not replay a consumed code automatically.
3. `setSession` is not a pure cookie setter: the [pinned Auth client](https://github.com/supabase/supabase-js/blob/v2.117.2/packages/core/auth-js/src/GoTrueClient.ts) checks the token and reads live user, or refreshes an expired pair. Likewise `getSession` can refresh near expiry even with automatic ticking disabled. **All cookie-sharing SDK clients need a refresh transport bridge**, not just `autoRefreshToken:false`.
4. Proposed bridge: intercept SDK refresh-grant fetches and invoke canonical A07 with RefreshTokenDTO; translate its successful token pair to the SDK's provider-session representation, loading the provider user with the fresh explicit access token. App AuthUserDTO is not a provider User object. This translation is internal memory, not an extra application DTO/route. Backend provider adapter uses an independent transport to avoid recursion. Canonical failures retain the original ErrorDTO for the UI; do not expose raw provider messages. Unknown credential/send/verify SDK calls outside the approved OAuth exchange are blocked from the migrated frontend path. This is a proposed adapter seam requiring pinned-version tests, not an existing bridge.
5. One refresh owner coordinates concurrent requests/tabs before consuming a token. Proxy/server reads and browser timers must share the bridge; disable competing proactive browser refresh. A protected request may refresh once and retry once on AUTH_REQUIRED/TOKEN_EXPIRED, with no refresh loop or replay of non-idempotent work after an ambiguous response. Publish both rotated cookies before navigation and preserve them on redirects. Read-only Server Components cannot be the refresh writer. Proxy currently calls `getUser()` (its getClaims comment is stale); retain live identity checks separately from app authorization.
6. Use a request-scoped bridge/provider-user lookup and no shared session singleton/cache. Propagate SSR `setAll` response cache headers as well as cookies; auth responses are private/no-store. Current cookie callbacks accept only cookies, dropping the pinned SDK's second cache-header argument. Do not claim CDN safety until verified. Preserve the SDK cookie format rather than hand-encoding tokens or minting another JWT.
7. Canonical A06 uses AZ-SUSP, current-session provider revocation (`scope:local`), no body and idempotent 200 while a valid JWT remains. [Pinned provider logout](https://github.com/supabase/auth/blob/v2.197.0/internal/api/logout.go) supports local scope. The current frontend's unscoped SDK signOut defaults to global. After canonical acknowledgment, clear SDK session/cookie chunks, private client caches and draft; any SDK cleanup logout transport must remain local and must not become a substitute for A06. On revocation outage, clear local state but report remote revocation unconfirmed. Missing JWT is still 401; repeated logout does not exempt authentication.

Provider rotation has a configured **10s reuse interval**. Do not promise rejection of every immediate replay; test supported grace/reuse detection and rejection after revocation/expiry. Silent A07 must load existing app state without bootstrap/activity writes and must not resurrect deleted/missing accounts. Suspended accounts can refresh into the settings shell; features remain denied. AuthSessionDTO keeps its two next_step values; OAuthSessionResponseDTO retains `add_verified_contact` as its third value. Routing priority: suspended → settings; OAuth verified-contact-required → settings prompt; otherwise profile setup hint or dashboard, with skip/basic dashboard access.

Logout revokes refresh, not the cryptographic validity of an issued access JWT. Current backend strategy has no session-revocation lookup. Proposed normal-route validation checks the provider session referenced by the signed token using a supported server-side session check; a live user lookup is not assumed to prove this until pinned-provider tests establish it. Keep A06's repeat behavior while rejecting revoked sessions for normal routes. If the supported provider cannot supply this check, document the access-token lifetime window and obtain a scoped requirement decision before immediate-revocation claims; no denylist table or schema amendment is authorized here.
