## Proposed canonical session handoff

Engineering proposal for M01-04/06/07/08 review; no new wire fields or internal HTTP endpoints. Retain the existing SSR cookie adapter/PKCE OAuth boundary. NestJS owns canonical validation, R31 counters/error translation, trusted provisioning and app state. The SDK owns session serialization/chunking and provider identity reads, not application policy.

1. Existing Next Server Actions send canonical A01/A02/A04/A05 DTOs to NestJS. Signup/resend return only RegistrationPendingDTO. A02/A05 return AuthSessionDTO only after live provider identity checks and successful app mapping. Do not return token payloads through client form state or store them in the R18 draft.
2. In a writable Server Action/handler, install the fresh canonical token pair with SDK `setSession({access_token, refresh_token})` using the existing request-scoped server client. Require success before redirect; retrieve app routing/status from canonical DTO/A13, never from cookie user metadata. If installation fails after provider success, retain no usable browser session and offer login recovery; do not replay a consumed code automatically.
3. `setSession` is not a pure cookie setter: the [pinned Auth client](https://github.com/supabase/supabase-js/blob/v2.117.2/packages/core/auth-js/src/GoTrueClient.ts) checks the token and reads live user, or refreshes an expired pair. Likewise `getSession` can refresh near expiry even with automatic ticking disabled. **All cookie-sharing SDK clients need a refresh transport bridge**, not just `autoRefreshToken:false`.
4. Proposed bridge: intercept SDK refresh-grant fetches and invoke canonical A07 with RefreshTokenDTO; translate its successful token pair to the SDK's provider-session representation, loading the provider user with the fresh explicit access token. App AuthUserDTO is not a provider User object. This translation is internal memory, not an extra application DTO/route. Backend provider adapter uses an independent transport to avoid recursion. Canonical failures retain the original ErrorDTO for the UI; do not expose raw provider messages. Unknown credential/send/verify SDK calls outside the approved OAuth exchange are blocked from the migrated frontend path. This is a proposed adapter seam requiring pinned-version tests, not an existing bridge.
5. One refresh owner coordinates concurrent requests/tabs before consuming a token. Proxy/server reads and browser timers must share the bridge; disable competing proactive browser refresh. A protected request may refresh once and retry once on AUTH_REQUIRED/TOKEN_EXPIRED, with no refresh loop or replay of non-idempotent work after an ambiguous response. Publish both rotated cookies before navigation and preserve them on redirects. Read-only Server Components cannot be the refresh writer. Proxy currently calls `getUser()` (its getClaims comment is stale); retain live identity checks separately from app authorization.
6. Use a request-scoped bridge/provider-user lookup and no shared session singleton/cache. Propagate SSR `setAll` response cache headers as well as cookies; auth responses are private/no-store. Current cookie callbacks accept only cookies, dropping the pinned SDK's second cache-header argument. Do not claim CDN safety until verified. Preserve the SDK cookie format rather than hand-encoding tokens or minting another JWT.
7. Canonical A06 uses AZ-SUSP, current-session provider revocation (`scope:local`), no body and idempotent 200 while a valid JWT remains. [Pinned provider logout](https://github.com/supabase/auth/blob/v2.197.0/internal/api/logout.go) supports local scope. The current frontend's unscoped SDK signOut defaults to global. After canonical acknowledgment, clear SDK session/cookie chunks, private client caches and draft; any SDK cleanup logout transport must remain local and must not become a substitute for A06. On revocation outage, clear local state but report remote revocation unconfirmed. Missing JWT is still 401; repeated logout does not exempt authentication.

Provider rotation has a configured **10s reuse interval**. Do not promise rejection of every immediate replay; test supported grace/reuse detection and rejection after revocation/expiry. Silent A07 must load existing app state without bootstrap/activity writes and must not resurrect deleted/missing accounts. Suspended accounts can refresh into the settings shell (contract requirement; current AuthService.refresh gates on active status via is_session_approved, so suspended token refresh remains open); features remain denied. AuthSessionDTO keeps its two next_step values; OAuthSessionResponseDTO retains `add_verified_contact` as its third value. Routing priority: suspended → settings; OAuth verified-contact-required → settings prompt; otherwise profile setup hint or dashboard, with skip/basic dashboard access.

Logout revokes refresh, not the cryptographic validity of an issued access JWT. Current backend strategy has no session-revocation lookup. Proposed normal-route validation checks the provider session referenced by the signed token using a supported server-side session check; a live user lookup is not assumed to prove this until pinned-provider tests establish it. Keep A06's repeat behavior while rejecting revoked sessions for normal routes (AuthService.logout is idempotent at the service layer; HTTP repeat-logout after revocation and first-time logout from an unverified account remain open because AccessGuard rejects unverified contacts and revoked sessions with 403 UNVERIFIED_ACCOUNT). If the supported provider cannot supply this check, document the access-token lifetime window and obtain a scoped requirement decision before immediate-revocation claims; no denylist table or schema amendment is authorized here.

## Password recovery, session revocation, phone contract, social linking and contact management (M02-01 / M02-02)

Engineering architecture for EP-A08, EP-A09, EP-A03, EP-A11, and EP-A12:

1. **EP-A08 (POST /auth/forgot-password):** Dispatches password reset challenge to the user's verified contact. Normalizes email or Bangladesh mobile number; reserves send quota in Redis (`3 / contact / 15 min`, `10 / IP / 15 min`, `60 s` cooldown); returns uniform `202` with message `If the account exists, a code was sent.` for both existing and unknown identifiers (anti-enumeration). Phone password recovery returns `503 SERVICE_UNAVAILABLE` while SMS provider is disabled.
2. **EP-A09 (POST /auth/reset-password):** Verifies 6-digit challenge code in `OtpSecretStore`, updates GoTrue password via admin endpoint inside the verification callback with local session revocation, consumes the OTP challenge, and revokes GoTrue sessions (`auth.sessions`) and refresh tokens (`auth.refresh_tokens`). Suspended users are denied with `403 ACCOUNT_SUSPENDED`. Password reset requires signing in anew upon refresh or outside the remaining unexpired access-JWT lifetime window.
3. **EP-A03 (POST /auth/verify-phone):** Verifies 6-digit SMS OTP challenge, confirms GoTrue phone user, updates `users.phone` and `users.verified_contact = true`, and mints authenticated session. Returns `503 SERVICE_UNAVAILABLE` while SMS adapter is disabled; synthetic integration test gate is Implemented in M02-02 (`backend/src/auth/phone-identity.integration.spec.ts`).
4. **EP-A11 (POST /auth/identities/link):** Authenticated user links Google or Facebook social identity. Requires `verified_contact = true` (unverified accounts rejected with `403 VERIFIED_CONTACT_REQUIRED`); prevents account collisions by rejecting existing provider links with `409 IDENTITY_LINK_CONFLICT`; wired to Screen 22 `IdentityLinkingCards` and verified in synthetic integration test gate (`phone-identity.integration.spec.ts`). Implemented in M02-02.
5. **EP-A12 (POST /auth/contact):** Authenticated user adds email or phone contact, creates unverified `user_auth_providers` record, and dispatches challenge code. Completed via EP-A02 or EP-A03 with JWT; wired to Screen 22 `AddContactForm` and verified in synthetic integration test gate (`phone-identity.integration.spec.ts`). Implemented in M02-02.
6. **R18 Storage Isolation & Security Invariants:** URLs never contain contact identifiers (`/reset-password` only); passwords, OTP codes, and tokens never enter `sessionStorage`; verification drafts maintain `min(challenge expiry, 10 min)` TTL and are cleared on password reset and sign-in.

1. **No External AI Call Inside Open DB Transactions (`R13`):** `PostgresJobQueueConsumer.claimBatch()` commits `queued -> preparing` (`FOR UPDATE SKIP LOCKED` on `idx_ai_requests_queue` using `available_at`) before `handler.execute()` runs. 2. **Two-Step Lease Recovery (`23514`):** `JobReaperService` and `PostgresJobQueueConsumer` never execute `preparing -> queued` directly (forbidden by `private.validate_ai_request_status()`).
