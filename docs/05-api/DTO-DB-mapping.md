## Pending account lifecycle proposal

**Conflict/evidence:** C05 EP-A01 requires `users` and `user_auth_providers` created in an unverified state at registration; A02 creates empty profile/preferences. Current code has no A01 and only provisions through JWT bootstrap with live Auth lookup, creating all four rows together. Confirmed-contact-only copying is correct trust behavior but does not implement A01 timing. C06 supports pending rows: contacts nullable, verified_contact defaults false, provider verified_at nullable; there is no requirement that active status means verified. C06 also requires the Auth UUID to exist first. No SQL change is needed just to represent pending state.

**Proposed smallest design:** after a genuinely new provider signup is confirmed by a trusted server response/lookup, serialize on that provider UUID and insert users with null confirmed contacts and verified_contact=false; insert the authoritative provider subject with unverified contact_value and verified_at=null. Leave login/activity timestamps unset and profile/preferences until successful A02. Email belongs in the unverified provider mapping, not the confirmed users.email. No new status/columns. At A02 validate live UUID/contact confirmation; update the same rows and create profile/preferences atomically, preserving status, ownership and existing data. Never use a client-posted UUID, unverified metadata, or a provider's obfuscated duplicate-signup response as proof of a new identity.

**Unresolved capability:** backend public-key plus bearer `/user` supports post-session bootstrap, not privileged pre-session reconciliation. Public signup may return an obfuscated duplicate user; there is no configured server-only admin adapter/credential consumer for trusted lookup before verification. Future adapter work must establish a supported least-privilege provider mechanism under explicit configuration/data approval. No credential is accessed or new env name invented here. If that mechanism is unavailable, A01 application-row timing needs an owner-reviewed scoped exception; silently deferring all application rows to A02 would not satisfy adopted C05. This affects M01-03/04; R31-only M01-02 does not depend on it.

## Non-atomic failures and duplicate requests

Provider calls occur outside the application DB transaction. Do not hold account locks over network calls or claim cross-system rollback. Auth owns passwords/challenges; PostgreSQL owns app mapping/access. Existing unique indexes and UUID transaction locks make same-identity application reconciliation idempotent, not every external call exactly once. These operations are not H-IDEM endpoints; do not add Idempotency-Key, challenge IDs or retry fields to their wire contracts.

| Failure / retry | Required recovery proposal and evidence still needed |
|---|---|
| Validation/mismatch/consent fails | No provider call or application row. Field details preserve valid UI input |
| Provider create/send fails or response is lost | Never mark verified or return session. Map explicit delivery failure to EMAIL_PROVIDER_ERROR 502; timeout/provider/database errors follow C05 §16.6. Ambiguous completion must be reconciled through trusted lookup before another create/send; send attempts remain counted and cooldown is not refunded |
| Auth user/challenge exists, pending app transaction fails | Leave provider account unverified; rollback all application rows. Do not delete an identity automatically: another valid retry might own it. Retry trusted reconciliation, then resend within limits. Public duplicate result stays CONTACT_ALREADY_REGISTERED 409; internally repairing a proven same identity must not create a second UUID |
| Provider verifies/consumes code, DB transaction fails | Withhold session from frontend; rollback app mapping. Code may already be consumed, so blind code replay cannot be the recovery mechanism. Use password login with live verified identity to repair mapping, then establish session; logout/discard any temporary provider session where supported. No browser token handoff before DB commit |
| Concurrent verify/repeated success | Atomic Redis compare/consume and provider verification serialize challenge use; DB locks/uniqueness prevent duplicate app/provider/profile rows. Consumed code must not create another session; use specified ALREADY_VERIFIED 409 when already verified, or invalid/expired code as evidenced by provider state. No invented replay error |
| Verified contact belongs to another account/provider subject collides | Fail closed; never merge by email/name. Existing bootstrap maps named 23505 indexes to IDENTITY_LINK_CONFLICT 409. A01 duplicate contact is CONTACT_ALREADY_REGISTERED 409. Preserve both UUIDs, rollback local writes |
| Refresh succeeds but response/cookie persistence fails | Old refresh may be rotated. Coordinate one refresh owner; reconcile supported reuse grace rather than retry indefinitely. If recovery fails, clear local session and require login; never replay signup/code as a refresh fallback |
| Logout provider fails | Clear local cookie/draft/private cache but remote revocation remains unconfirmed; preserve safe retry/error. Current-session revocation cannot be described as immediate access-JWT invalidation |

## Contract precision findings

Canonical [OpenAPI](openapi.yaml) follows C05 §15.1: optional retryAfterSeconds is an integer ≥0. Current HTTP fail/filter emits null when absent, and frontend accepts it. This observed discrepancy is recorded for a future bounded implementation/review decision; the canonical schema does not silently adopt null. The transitional sync operation explicitly documents its observed error variant. C05 registration example has phone:null although the field table calls the unused contact conditional string; the shared schema permits omitted or null unused contact, with exactly one actual string. This is source-based reconciliation, not permission to accept two contacts.

No new consent persistence, challenge table, session table, provider choice, deletion design or SQL amendment is part of this mapping. Recovery scenarios are **planned acceptance cases**, not executed outcomes; see [QA Q05/Q08/Q09](../08-testing/QA-plan.md).
